# CT4 手动历史修订

在传感器详情录入/修正当前探头二维码，然后点击现有“历史”按钮并确认。
二维码更新本身不批量覆盖历史。其他 Anytime 家族的历史按钮仍使用原有读取行为。

## 操作范围

- 确认时固定佩戴周期 UUID、二维码配置、Unix 时间轴及最新已证明的实时 ID。
- 从 ID 0 重新请求原始数据，手动操作不跳过已缓存记录。
- MK4 使用独立计算器按 ID 升序重放；历史计算不推进实时滤波器。
- 只覆盖本次实际重新读到、位于确认截止点内、具有从 ID 0 开始完整原始前缀且通过预热/有效性检查的记录。
- 缓存中相同佩戴周期的原始数据可以补充计算前缀。缺失前缀后的记录保留原值，不以临时尾段模型覆盖。
- Room 按同一传感器、同一分钟替换数值，保留首次存储时间；仅使成功修订分钟的旧显示值失效。未读到的分钟、其他传感器、旧佩戴周期均保留。
- 始终使用原来的 `timelineStart + glucoseId * 180000`。没有 +1 小时、−75 秒或时区重复转换。

任务及已读/已写 ID 集合保存在当前佩戴周期的本地首选项。BLE 中断后恢复范围；进程重启后从零重新请求，避免首选项与原始缓存分别落盘产生缺口。重复读取不会产生新的记录身份。
手动启动与重启恢复均等待本次 BLE 连接实际收到并通过周期检查的实时原始记录；仅凭恢复的旧缓存或握手成功不足以确认当前探头。
若重算中更换二维码，停止旧任务，需再次确认“历史”。疑似实时 ID 大幅回滚时先暂停历史读取，待确认物理探头周期；确认新周期后归档旧任务，旧确认不适用于新探头。无需硬件解绑或结束探头。

## 上报

成功修订批次沿用现有 Room → native 镜像 → Health Connect/Nightscout 唤醒路径。
native 的已存在血糖值发生变化时，也回退 Health Connect 游标并使正在上传的旧快照失效；相同数值重放不反复回退。

Health Connect 保持原来的 `juggluco-ng:glucose:<sensor>:<epoch-second>` 标识，以独立 SQLite 账本保存各记录的数值和版本。同一数值重试/重启复用版本，改变数值时版本单调增加，即使系统时钟回退也成立。一个上传批次只使用一个本地事务；插入失败不确认 native 游标。升级前的版本 0 会被更高版本替换，不需清空应用或健康平台数据。
参见 [Health Connect 官方修订规则](https://developer.android.com/health-and-fitness/health-connect/write-data#value-check)。

Nightscout 继续使用现有发送器和稳定标识，数值/Raw 修订回退发送游标。服务端去重、权限和 API 版本会影响实际覆盖结果；本改动不宣称已验证某个真实 Nightscout 服务器的覆盖行为。Health Connect 真机覆盖、CT4 长历史重读、与实时 BLE 并行和中途换探头仍需用户设备验证。

Samsung Health 维持此前确定的直接只读与整合全量导出，不新增血糖写入。SDK 与包含 SDK 的个人 APK 继续留在本地。

## 回归覆盖

`AnytimeManualHistoryRewriteTest` 覆盖任务范围、完整前缀、重启、取消、同优先级修订、乱序重复读取、缺口与实时滤波隔离。
`HealthConnectRecordVersionsTest` 使用真实 SQLite 主机模拟环境验证版本落盘、重试、回退时钟、批次回滚及跨时区标识/时间不变。
`RecordedDisplayVoidingTests` 覆盖部分修订时保留未收到的分钟及其他传感器。
`HealthConnectCursorTests.cpp` 覆盖已有值修订、上传中修订、重复值与无效值不回退、补洞和旧快照拒绝。
